2. Understand the machine and its layers

Begin with a physical question: what happens if your application stops? For a temperature-controlled training tank, a sensor measures temperature, an input module converts its signal, a PLC executes the control program, and an output drives a heater through appropriate electrical equipment. An HMI shows the operator what is happening. A historian records measurements. A manufacturing system relates the run to a batch and product.

A PLC is an industrial controller. An HMI is the operator interface. SCADA provides supervisory control and data acquisition across equipment. MES manages manufacturing execution such as work orders, traceability and production records. ERP manages enterprise resources and transactions. These are responsibilities, not a law requiring one server per box. Products may combine them. Our architectural choice is to keep register addresses and controller quirks inside a device adapter.

3. Timing, scans and observations

A deadline is different from an average response time. A task that usually finishes in 2 ms but sometimes takes 200 ms cannot satisfy a 10 ms bound. Industrial systems include hard, firm and soft timing requirements; the classification comes from the consequence of a missed deadline. No universal millisecond limit separates them.

In the simple cyclic model, the controller samples inputs, evaluates logic and updates outputs. An input changing just after sampling waits almost one cycle to be sampled, then waits for computation and output update. Real controllers can also have periodic tasks, interrupts, asynchronous I/O and communication services. Beckhoff’s documentation explicitly describes task priorities, CPU assignment and cycle times; “PLCs have no operating system or scheduling” is not an accurate general explanation. [P1]

Budget the whole observation path

For an illustrative monitor, suppose input conversion takes at most 8 ms, control-data publication 20 ms, the next poll 250 ms, a response 40 ms and the next display refresh 200 ms. A simple serial upper estimate is 518 ms. This is only a teaching sum: an engineering bound also needs scheduling jitter, clock assumptions, failures and the actual controller’s timing model. It is not a certified worst-case analysis.

250 ms poll → 518 ms illustrative observation delay

Fixed illustrative contributions: 8 + 20 + 40 + 200 ms. Shortening the poll affects only one part of the path.

Choose acquisition rates from the signal’s bandwidth, the shortest event you must observe, acceptable age, controller capacity and network load. A rule such as “poll at twice the scan period” is not a sampling theorem. Faster polling can reduce observation latency without discovering a new value every time. Slower polling can miss an entire pulse. If a sensor pulse lasts 15 ms and you poll every 250 ms, use a controller-side latch, counter or event buffer instead of hoping your poll catches it.

For vibration or fast motion, a dedicated acquisition device may sample at high rates and deliver blocks with timestamps. The HMI can draw a summary at a much slower rate. Similarly, OPC UA source updates, monitored-item sampling and subscription publishing are separate schedules; the server may revise your requested intervals. Subscriptions do not promise that every physical transition will be observed. [P2]

What C# should promise

An ordinary .NET application on a general-purpose operating system should promise measured service objectives, such as an acceptable sample-age distribution, recovery time and bounded memory usage. It should not claim a hard real-time guarantee because it uses asynchronous methods or a high-priority thread. Keep a protective function in an appropriately engineered control or safety system. A normal PLC is not automatically a safety controller either.

Record latency histograms, maximum sample age and missed deadlines separately. Wall-clock UTC timestamps help correlate equipment. A monotonic clock measures elapsed time even if the system clock changes. The supplied lab uses TimeProvider.GetTimestamp() for current-sample age. Reading a cached value must never reset the time at which it was acquired.

Check your understanding

A 1-second temperature poll may be adequate for one slow process and inadequate for another. You need the process dynamics and required response, not a universal temperature sampling number. An unchanged value is also not proof of a broken link; look for acquisition timestamps, sequence and connection health.

Two rules follow. First, polling can only observe a state that persists for longer than the poll period plus the publishing granularity; an event must be captured at the source as a counter, latch or timestamped buffer. Second, the counter’s observation latency is still bounded by scan + poll + transport (the demo reports a maximum of 112 ms for the default run), so a counter tells you that something happened, not precisely when. If you need event time, the PLC must timestamp it.

A common misconception is to invoke the sampling theorem here. Nyquist–Shannon concerns reconstructing a band-limited continuous signal from samples. A discrete pulse is not band-limited and you are not reconstructing it; you are asking whether a sample landed inside it. Reason about windows and probabilities, as the simulator does, rather than “sample at twice the frequency.”

Exercise: predict before you run

With a 10 ms scan and a 15 ms pulse, the published bit stays high for one or two scan periods, i.e. 10–20 ms. A 100 ms poll with a random phase therefore lands inside it roughly 10–20% of the time; the demo’s 6 of 50 (12%) is consistent. Change --seed a few times and watch the live-bit count vary while the counter stays exactly 50.

Modbus essentials

Coils and discrete inputs represent bits; holding and input registers represent 16-bit words. Conventional human references such as 40001 are not necessarily the numeric address passed to a client library. With a device whose first holding register is called 40001, its protocol offset is commonly 0. Confirm the manual and library convention. Do not transmit 40001 because it appears in a spreadsheet.

The course examples use function 03 to read holding registers. Registers do not carry engineering units or source timestamps. A successful transport response means bytes arrived—not that the sensor is healthy or the mapping is correct. Traditional Modbus TCP also does not, by itself, authenticate an operator or encrypt traffic. Use the site’s controlled network architecture and supported secure options.

The original article uses NModbus4. For a new evaluation, examine the NModbus project [P3], a fork of NModbus4, and pin the version you test. Its APIs differ. This handbook does not substitute an untested package command for a verified device integration. The supplied framing exercise has no connection to a PLC and is deliberately not a complete Modbus driver.

OPC UA essentials

Use the OPC Foundation’s .NET implementation [P4] as a reference implementation to evaluate. Learn endpoint discovery, application certificates, trusted peers, user identity, browsing, reading and subscriptions in that order. Use a test server and a separate browsing client before introducing your own abstraction.

A NodeId’s namespace index can change. Persist the namespace URI with the identifier and resolve the current index after connecting. Read the returned data type and status. Reject or label bad values instead of silently converting null to zero. Engineering-unit metadata is useful when the server actually supplies it; OPC UA does not create missing semantics automatically.

Record revised sampling and publishing intervals, queue sizes, overflow indications and reconnect outcomes. Test a disconnected session and a restarted server. A successful reconnection does not prove that subscriptions resumed or that gaps were backfilled. Do not disable certificate validation to make a deployment “work.”

MQTT belongs above acquisition in the proposed design

Publish normalized events such as factory/site-a/tank-01/telemetry, with a stable event ID, timestamp, quality and schema version. A retained value may be old; its presence is not liveness. QoS 1 can redeliver a message. Even QoS 2’s protocol delivery behavior does not make a database transaction or physical command execute exactly once. Give consumers an idempotency key. [P5]

Deep dive · the Modbus details that cause real bugs

Four tables, function codes and limits

Modbus exposes four logical tables. Every “address” is a zero-based offset inside one of them, carried as a 16-bit number in the request. The five-digit references (00001, 10001, 30001, 40001) are a documentation convention that encodes the table and starts counting at 1. A manual that says “temperature at 40001” usually means holding-register offset 0. Record both forms in your device contract; an off-by-one here produces plausible-but-wrong values rather than errors. [P25]

Modbus TCP versus Modbus RTU framing

Modbus TCP puts a seven-byte MBAP header (transaction, protocol, length, unit) in front of the PDU and relies on TCP for integrity; the length field is what delimits a frame, as Chapter 6 shows. Modbus RTU on RS-485 has no length field. It ends every frame with a CRC-16 and delimits frames by silence: a gap of at least 3.5 character times, with a fixed 1.75 ms floor at higher baud rates. [P26] That makes RTU framing a timing problem on the receiving side — the one place in this course where a timing rule legitimately defines message boundaries. USB–serial adapters that buffer bytes, and operating-system scheduling, can stretch or hide those gaps; use a driver or library that is designed for RTU rather than a SerialPort loop with Sleep. One RS-485 bus also carries one conversation at a time, so a poll schedule for 20 devices is a queue, and its length bounds your freshness.

5. Decode numbers and bits correctly

Separate three representations: bytes on the network, numeric words returned by a library, and the physical value those words encode. A Modbus library returning ushort values has already decoded each word. Calling BitConverter.GetBytes on that word introduces the host’s byte order again. This distinction is the reason apparently sensible endian helpers can be wrong.

Use a known 32-bit bit pattern with four different bytes: 0x42F6E979, approximately 123.456 as an IEEE 754 single. Define A as its most significant byte and D as its least significant byte. Our contract for the layout names is:

Explore a register pair

Boolean meaning does not define the wire layout

A logical Boolean represents true or false. Its storage and interchange format depend on the runtime, mapping and protocol. Beckhoff, for example, documents both single-bit addressing and byte allocation when no single-bit address is specified. Its BIT type has its own rules. These are vendor-specific facts, not proof that every PLC Boolean or every EtherCAT field occupies one byte. [P6] [P7]

For a documented packed byte 0x05 (00000101), bits 0 and 2 are set. Test a bit with (value & (1 << index)) != 0 and validate the index. For a documented byte Boolean, follow the device’s allowed encodings; do not universally assume every nonzero code means true. Modbus’s single-coil write, for example, has a specific ON encoding rather than accepting an arbitrary nonzero register value. Never infer a native interop structure layout from a C# bool[].

Multi-register values introduce another issue: consistency. If the device updates halves of a value separately, one read can observe a mixed snapshot. Use the vendor’s atomic-read guarantee, a controller snapshot buffer, or a documented version/sequence handshake. Byte-order correction cannot repair a torn value.

Lab checkpoint: verify 25.5, a negative number and the four-byte test pattern. Preserve NaN and infinity long enough for validation to mark the sample invalid; never replace them with zero and call it good data.

6. Read streams without timing guesses

TCP transports an ordered byte stream. One send can arrive in several reads; several sends can be available in one read. A delay may change how many bytes happen to be waiting, which explains why an added Sleep can appear to fix a bug. It does not create message boundaries. Microsoft documents that NetworkStream.ReadAsync can return fewer bytes than requested; zero on a nonempty read indicates graceful peer shutdown. [P8]

In the supplied teaching parser, read six bytes of a Modbus TCP header, extract the declared length, validate it, then read exactly that many more bytes. The length covers the unit identifier plus the protocol data unit. Validate the transaction ID, protocol ID, unit, function and response byte count. Preserve following frames for the next transaction. A normal library handles this framing for you; this exercise teaches what its contract must achieve.

Request context: transaction 7, unit 1, function 03, two registers

                 └ ID ┘ └ P ┘ └len┘ U  F  N └ register data ┘

Use one overall deadline for the operation, with cancellation covering both header and body. A timeout or malformed frame should leave the connection in a known state; the simple strategy is to close and reconnect before the next transaction. Retrying a read is different from retrying a write whose outcome is unknown. An exception response is a valid protocol frame reporting failure; report its code rather than parsing it as register data.

What a ring buffer does and does not do

A ring buffer retains bytes between reads. It still needs a parser that knows frame boundaries. It also needs an unambiguous full/empty representation and an overflow policy. With only (write - read + capacity) % capacity, both an empty buffer and a completely full buffer can appear to contain zero bytes. The source article’s example permits filling the entire capacity and therefore hits this ambiguity.

Fix that design by keeping an explicit count, reserving one slot, or using another proven invariant. For a protocol stream, silently dropping bytes destroys framing. Fail the connection or apply backpressure according to the design. Dropping old display samples is a different, often reasonable, policy. The lab avoids a custom ring buffer and uses exact-length reads with bounded allocations.

What the framing tests prove

The tests feed the parser one byte at a time, feed two joined frames, truncate a frame, corrupt its length, transaction and byte count, return a device exception, and cancel a read. They prove these parser behaviors against synthetic streams. They do not prove device interoperability or network performance.

Deep dive · from a parser to a poller

What a complete request/response cycle must do

The parser above reads one response. The new ModbusTankPoller in the lab wraps it in the minimum a real client needs. Read PollOnceAsync alongside this list:

  1. One deadline for the whole exchange. A linked CancellationTokenSource with CancelAfter covers connect, write, header read and body read. Separate per-read timeouts let a slow trickle of bytes extend the exchange indefinitely.
  2. A new transaction ID per request. The ID is a ushort that wraps after 65,535; that is fine because only one request is outstanding. The parser rejects a response whose ID does not match.
  3. After a timeout, close the connection. The device may still answer request 17 after you gave up. If you keep the socket and send request 18, the next bytes to arrive belong to 17. With a transaction check you get a confusing error; without one you get the previous answer presented as current data. Closing and reconnecting discards the late reply.
  4. Back off before reconnecting. Capped exponential backoff with jitter (250, 500, 1000 … 8000 ms, each scaled to 50–100%) stops a fleet of clients from hammering a recovering device in lock-step.
  5. Keep the last good value, but never re-label it. A failed poll returns the previous reading with BadCommunication and its original LastGoodTime.

Modbus TCP permits several outstanding requests matched by transaction ID, but many devices and gateways process one at a time and some mishandle pipelining. Only pipeline when the device documentation says it is supported and you have tested it; the throughput gain is rarely worth the new failure modes.

The half-open connection

If a switch loses power or a cable is cut, neither end of the TCP connection may learn about it: no FIN or RST ever arrives. A read with no deadline then waits indefinitely, and operating-system keepalive defaults are measured in hours. This is why the lab treats “no complete response within the deadline” as a communication failure, rather than waiting for the socket to report an error. Lab 14 creates exactly this situation with the /lab/link/false switch: the device silently swallows requests.

7. Build a trustworthy acquisition service

The acquisition service is your semantic boundary. Below it are registers, symbols, timeouts and firmware quirks. Above it are named assets, values with units, state observations and documented quality. OpenClaw.NET tools should consume the latter and present it through AgentQi Companion or another supported interface.

Device adapter → decode → validate → timestamp and quality → fan-out
                                                      ├ latest-value cache
                                                      ├ historian or durable spool
                                                      ├ alarm evaluator
                                                      └ business event publisher

Use one connection owner or explicitly supported serialization per device. A timer callback must not start a second read while the previous one still owns the connection. PeriodicTimer with an awaited loop is a useful ordinary .NET pattern; it is not a real-time scheduler. Maintain bounded queues between independent consumers. A single channel with several readers distributes items among readers; it does not broadcast every item to everyone. Create explicit fan-out if each consumer needs all samples.

.NET’s channels support wait, drop-oldest, drop-newest and drop-write policies. Choose these deliberately: a live chart might keep only recent samples, while an audit event needs a durable path and explicit failure reporting. An in-memory channel alone is not a historian and does not survive a restart. [P9]

Worked failure: the last temperature is 54 °C at 10:00:00. Communications fail at 10:00:01. At 10:00:05, return the last value with its original timestamp and bad/stale quality. Do not return 0 °C, and do not attach 10:00:05 as though that were the measurement time. An agent must be able to say, “The latest available sample is five seconds old; I cannot verify the current temperature.”

Use a configurable stale threshold per tag or class of signal. On a reconnect, validate identity and mapping, then acquire a fresh sample before returning to Good. Track poll duration, consecutive failures, reconnect count, queue depth, dropped display samples, spool occupancy and last successful acquisition. Use capped exponential backoff with jitter, but coordinate it with the user-visible freshness requirement.

Design exercise: if acquisition produces 1000 samples/s and storage handles 800/s, the backlog grows by 200/s. A 10,000-sample buffer buys only 50 seconds. A bigger buffer delays failure; it does not fix insufficient sustained throughput.

Deep dive · quality is a small, explicit state machine

Five outcomes, five different messages

“Is the value good?” has more than two answers, and each answer leads to different action. The lab poller implements the following classification; an agent or screen should phrase each one differently.

QualityDetected byWhat a person or agent should say
GoodComplete, well-formed response; expected mapping; finite value; heartbeat changed recently.“Tank temperature is 41.2 °C as of 10:04:07.”
StaleDevice answers promptly, but its heartbeat has not changed for N polls.“The device is responding, but its data stopped updating at 10:03:55. Treat values as frozen.”
BadCommunicationTimeout, EOF, socket error or malformed frame.“No data since 10:03:55 (5 failed attempts). Last known 40.8 °C; current value unknown.”
BadConfigurationDevice reports a different mapping version.“The device map changed (v2, expected v1). Values are not being decoded until the contract is updated.”
BadSensorValue decodes but is non-finite or physically impossible.“Temperature sensor reading is invalid; the device itself is communicating.”

Stale deserves emphasis because it is the failure that looks healthy. A gateway, OPC server or PLC task can keep answering with cached values after its own upstream source has stopped. Response time is perfect; the numbers are fiction. The only defence is a value that must change while the source is alive — a heartbeat counter generated by the source itself, not by the gateway. The lab device publishes one in register 8, and the /lab/modbus/freeze switch reproduces the fault. Because the counter is a wrapping uint16, compare for change, never for “greater than”: 65535 → 0 is progress.

A mapping check guards the other quiet failure. After a PLC program download, the same registers can mean something else. Publishing a mapping version in a fixed register, and refusing to decode on mismatch, turns a silent semantic error into a loud configuration error. The poller refuses to return values at all in that state — returning numbers “just in case” is how a flow rate ends up plotted as a temperature.

8. Store measurements and business facts

Different records serve different questions. Configuration answers “what is this tag?” Measurements answer “what happened over time?” Alarms answer “which condition required attention?” Production events answer “what was made?” Audit records answer “who requested and authorized what?” Keep those meanings distinct even if an early prototype stores them in one database.

SQLite is useful for a local study project and many embedded applications. Use transactions, indexes and measured workloads before deciding it is too small. WAL can let readers and a writer proceed concurrently, but it does not create unlimited parallel writers. Enable it with an actual PRAGMA journal_mode=WAL; operation and inspect the result. Mode=ReadWriteCreate merely controls opening/creation behavior; it is not a WAL setting. Plan checkpointing and proper backups that account for WAL state. [P10]

Capacity before products

For 200 tags at 5 samples/s, the maximum unsuppressed rate is 1000 samples/s, or 86.4 million/day. At an illustrative 40 bytes/sample that is 3.456 GB/day before indexes, record overhead, replication and compression. These numbers are a sizing exercise, not a database benchmark. Estimate a retention budget and measure with representative writes and queries.

A time-series database can make retention, aggregation and time-range queries convenient. It is not automatically required above a fixed number of rows. If evaluating InfluxDB, match the client and query language to the chosen generation: the source article’s bucket/org/Flux example belongs to the InfluxDB 2 style; InfluxDB 3 does not support Flux. [P11]

Decide which information may be aggregated. For a one-minute window, save count, min, max, mean and quality coverage when appropriate. A mean alone can erase a short excursion. Keep event transitions independently of a trend’s downsampling. Do not interpolate a missing interval and then present it as measured data.

Reliable delivery to MES

Suppose a batch-completed event is committed locally but the MES call times out. You do not know whether MES processed it. Give the event a stable ID and make the receiver deduplicate it. A transactional outbox records the event in the same local transaction as the business change; a worker delivers it later and records acknowledgement. This is a proposed pattern for this architecture. It trades immediate availability for recoverable delivery and explicit retry behavior.

Use EF Core where tracked business entities and migrations help, and targeted SQL or Dapper where direct queries are clearer. Neither tool removes the need to batch writes, inspect query plans or manage transactions. Avoid sharing a mutable database context between concurrent workers.

From conceptual schema to verified SQL

The conceptual schema above is now a runnable one in labs/historian/schema.sql, with seven annotated statements in queries.sql and a checker, verify-historian.py, that needs only Python’s standard library. Key design decisions, each visible in the file:

  • Integer millisecond timestamps in UTC. They sort, index and subtract cheaply; convert for display only.
  • The primary key is (tag, boot, sequence) and inserts use INSERT OR IGNORE. A replayed batch after a crash is harmless rather than duplicated.
  • Bad samples are stored with NULL value and their quality. A gap with a reason is evidence; a silently missing row is not.
  • One index serves the dominant query: (tag_key, receive_ms). EXPLAIN QUERY PLAN confirms SEARCH sample USING INDEX sample_by_time for a window query.
  • The outbox row is inserted in the same transaction as the batch update, guarded by changes() = 1, so completing a batch twice produces one event.

Why batching matters more than the database brand

Each committed transaction must reach durable storage. Insert samples one per transaction and throughput is bounded by how many flushes the disk completes per second; insert 500 per transaction and the same flush covers 500 rows. Decide that trade-off per record type: losing the last second of a trend may be acceptable, losing a completed batch record is not. Keep observed state, requested action and workflow state separate. The controller may report Heating. A user may request Stop. The command may be AwaitingAcknowledgement. Combining those into one Boolean such as IsRunning makes failures impossible to describe accurately.

An alarm has a lifecycle

Imagine a supervisory high-temperature condition activates at 65 °C and clears at 63 °C. That hysteresis prevents chatter around one threshold. Add an on-delay only when the process requirement allows it. Acknowledging an active alarm records that someone has seen it; it does not clear the process condition. Record activation, acknowledgement, return to normal and any shelving as separate events.

If the temperature quality becomes bad, you cannot conclude the high-temperature condition cleared. Preserve the appropriate alarm state and raise or display the communication issue. Protective trips have separate engineering requirements; a C# threshold check or AI explanation is not their substitute.

Commands need outcomes

Proposed → Approved → Dispatched → Accepted → Completed
             ↓             ↓          ↓
          Expired        Unknown     Rejected / Failed

These are proposed application states. “Unknown” is essential: a connection can fail after the controller acts but before acknowledgement arrives. Blindly resending may repeat an operation. A device contract should define command IDs, command parameters, acknowledgement, result and recovery behavior. When supported, a mailbox-style handshake lets the PLC accept a command once and report the same result on a retry. Such a contract must be engineered with the PLC programmer.

Elsa or another durable workflow engine becomes relevant for long-running human work: assigning an investigation, waiting for evidence, escalating overdue work and recording completion. Keep that workflow separate from the machine’s cyclic program. Do not restart equipment automatically because a maintenance ticket was closed.

Three rules are enforced by tests. Acknowledgement never clears an active condition. A bad-quality sample never produces a return to normal — the alarm holds its state, records QualityBad once, and records QualityRestored when good data returns. And the gap between the set limit (65 °C) and the clear limit (63 °C) prevents chattering: in the self-test, values 65, 64, 65, 64, 65 produce one activation instead of three. An on-delay is also available (a value must stay above the limit for the whole delay), and it is tested to ignore a one-second excursion under a two-second delay.

Real alarm systems add shelving (an operator temporarily hides a nuisance alarm, with an automatic expiry), suppression by design (hide a downstream alarm while its cause is already alarmed), and out-of-service. Those are listed as extension exercises in Lab 8.

Controller alarm versus supervisory alarm

The simulator now has both, on purpose. The controller alarm bit (status register bit 3) is evaluated on the true temperature inside the simulated equipment and keeps working when communications fail. The supervisory HighAlarm sees only received samples, so during a link outage it can only say “evidence lost.” That asymmetry is why protective functions belong in the controller or safety system, and why a supervisory screen must show communication state next to alarm state.

How many alarms is too many?

Alarm-management guidance built on ISA-18.2 commonly cites about 150 alarms per operator per day (about one per ten minutes) as very likely acceptable and about 300 per day (about two per ten minutes) as the maximum manageable. [P27] Treat them as design targets for your alarm philosophy, not as a certification test for a lab. Their practical message is that every alarm needs a defined operator response; a condition that needs no response is an event for the log, not an alarm.

14. Move from study to a plant integration

The simulator teaches contracts and failure handling. It does not qualify a machine, electrical design or safety function. A production integration needs a controls engineer’s device contract and the site’s operational requirements. Work from those concrete requirements; do not promote the toy tank’s limits into real process limits.

A proposed command boundary

Split proposal, approval and execution into separate privileges. Bind a reviewed command to its asset, parameters, units, actor, approval identity, expiry, mapping version and relevant state/recipe preconditions. Persist that record before dispatch. Revalidate authorization, expiry and current preconditions at execution. Use a single owner for dispatch and a recoverable command state machine.

The approval must cover the exact content being executed. If someone changes the target after approval, invalidate the approval. An agent must not approve its own proposal, and an “approve=true” argument supplied by the model is not evidence of approval. If a controller acknowledgement is lost, reconcile using the command ID and controller feedback. Acceptance scenarios

  • Unplug communications: the last value is preserved and quality degrades; no request silently changes into a command.
  • Restart the gateway: history gaps and command recovery are explicit; old approvals do not unexpectedly run.
  • Change a mapping or controller revision: incompatible interpretations are blocked or clearly flagged.
  • Lose an acknowledgement: the request becomes uncertain and is reconciled without blind repetition.
  • Inject an alarm flood or a slow database: memory and queues remain bounded and loss is reported.
  • Give an agent a misleading manual or stale sample: it does not treat those contents as permission or verified current evidence.

The value of the AI layer should be assessed separately from communication reliability. Track unsupported-claim rate, correct source/asset selection, correct abstention on missing data and time to useful investigation. A fluent answer is not a successful incident response.

Appendix A. Tested C# decoder and parser

This is the exact Wire.cs source shipped in the lab. It is original teaching code. The parser handles one expected function-03 response on an already available stream; it does not establish a connection, send requests, schedule transactions or provide a production driver. Supply an operation deadline through its cancellation token and close/recover a failed transport before reusing it. This edition adds a request builder, uint32 and int16 decoding and a 16-bit bit test. ModbusPoller.cs shows the parser inside a complete request/response cycle; see Lab 13.

using System.Buffers.Binary;

namespace IndustrialLab;

public enum ByteOrder { ABCD, BADC, CDAB, DCBA }

public static class Wire
{
    // Inputs are numeric ushort values already decoded by a Modbus library.
    // Reconstruct wire bytes explicitly; do not call GetBytes(ushort) first.
    private static void ToCanonical(ushort reg0, ushort reg1, ByteOrder order, Span<byte> canonical)
    {
        Span<byte> raw = stackalloc byte[4];
        BinaryPrimitives.WriteUInt16BigEndian(raw[..2], reg0);
        BinaryPrimitives.WriteUInt16BigEndian(raw[2..], reg1);
        switch (order)
        {
            case ByteOrder.ABCD: raw.CopyTo(canonical); break;
            case ByteOrder.BADC:
                canonical[0] = raw[1]; canonical[1] = raw[0];
                canonical[2] = raw[3]; canonical[3] = raw[2]; break;
            case ByteOrder.CDAB:
                canonical[0] = raw[2]; canonical[1] = raw[3];
                canonical[2] = raw[0]; canonical[3] = raw[1]; break;
            case ByteOrder.DCBA:
                canonical[0] = raw[3]; canonical[1] = raw[2];
                canonical[2] = raw[1]; canonical[3] = raw[0]; break;
            default: throw new ArgumentOutOfRangeException(nameof(order));
        }
    }

    public static float DecodeFloat(ushort reg0, ushort reg1, ByteOrder order)
    {
        Span<byte> canonical = stackalloc byte[4];
        ToCanonical(reg0, reg1, order, canonical);
        return BitConverter.Int32BitsToSingle(BinaryPrimitives.ReadInt32BigEndian(canonical));
    }

    // Same permutation, different interpretation: the layout name describes bytes, not the type.
    public static uint DecodeUInt32(ushort reg0, ushort reg1, ByteOrder order)
    {
        Span<byte> canonical = stackalloc byte[4];
        ToCanonical(reg0, reg1, order, canonical);
        return BinaryPrimitives.ReadUInt32BigEndian(canonical);
    }

    // A register is 16 raw bits. Whether it is signed is part of the device contract.
    public static short DecodeInt16(ushort register) => unchecked((short)register);

    public static bool Bit(byte packed, int bit)
    {
        if (bit is < 0 or > 7) throw new ArgumentOutOfRangeException(nameof(bit));
        return (packed & (1 << bit)) != 0;
    }

    public static bool Bit(ushort word, int bit)
    {
        if (bit is < 0 or > 15) throw new ArgumentOutOfRangeException(nameof(bit));
        return (word & (1 << bit)) != 0;
    }

    // Builds a Modbus TCP request: MBAP header (7 bytes including unit) + FC03 PDU (5 bytes).
    public static byte[] BuildFc03Request(ushort transactionId, byte unitId, ushort startOffset, ushort registerCount)
    {
        if (registerCount is < 1 or > 125) throw new ArgumentOutOfRangeException(nameof(registerCount));
        byte[] frame = new byte[12];
        BinaryPrimitives.WriteUInt16BigEndian(frame.AsSpan(0), transactionId);
        BinaryPrimitives.WriteUInt16BigEndian(frame.AsSpan(2), 0);       // protocol ID: Modbus
        BinaryPrimitives.WriteUInt16BigEndian(frame.AsSpan(4), 6);       // unit + function + 4 data bytes
        frame[6] = unitId;
        frame[7] = 0x03;
        BinaryPrimitives.WriteUInt16BigEndian(frame.AsSpan(8), startOffset);
        BinaryPrimitives.WriteUInt16BigEndian(frame.AsSpan(10), registerCount);
        return frame;
    }

    // Demonstrates framing on a single outstanding FC03 transaction, not a complete driver.
    public static async Task<ushort[]> ReadFc03Async(Stream stream, ushort transactionId,
        byte unitId, int registerCount, CancellationToken cancellationToken)
    {
        if (registerCount is < 1 or > 125) throw new ArgumentOutOfRangeException(nameof(registerCount));
        byte[] prefix = new byte[6];
        await stream.ReadExactlyAsync(prefix, cancellationToken);
        ushort length = BinaryPrimitives.ReadUInt16BigEndian(prefix.AsSpan(4));
        if (length is < 2 or > 254) throw new InvalidDataException("Invalid MBAP length.");
        if (BinaryPrimitives.ReadUInt16BigEndian(prefix) != transactionId ||
            BinaryPrimitives.ReadUInt16BigEndian(prefix.AsSpan(2)) != 0)
            throw new InvalidDataException("Unexpected transaction or protocol ID.");
        byte[] payload = new byte[length]; // length includes unit ID and PDU
        await stream.ReadExactlyAsync(payload, cancellationToken);
        if (payload[0] != unitId) throw new InvalidDataException("Unexpected unit ID.");
        if (payload[1] == 0x83)
        {
            if (length != 3) throw new InvalidDataException("Malformed exception response.");
            throw new InvalidDataException($"Modbus exception 0x{payload[2]:X2}.");
        }
        if (payload[1] != 3 || length != 3 + 2 * registerCount || payload[2] != 2 * registerCount)
            throw new InvalidDataException("Unexpected function or byte count.");
        ushort[] registers = new ushort[registerCount];
        for (int i = 0; i < registerCount; i++)
            registers[i] = BinaryPrimitives.ReadUInt16BigEndian(payload.AsSpan(3 + i * 2));
        return registers;
    }
}

Lab 6 · Stale data

Goal: prove the service never presents old data as new.

  1. Start the service. In a second terminal, take a baseline: $a = Invoke-RestMethod http://localhost:5088/api/snapshot; $a.quality; $a.sample.sequence; $a.sample.receivedTimestamp
  2. Pull the link: Invoke-RestMethod http://localhost:5088/lab/link/false -Method Post

  4. Check the alarm view: (Invoke-RestMethod http://localhost:5088/api/alarms).recentEvents | Select-Object -Last 1
  5. Restore: …/lab/link/true. Snapshot twice more.

Expected: during the outage, sequence and received timestamp are frozen at the last acquisition, ageMs grows by about 2000 per snapshot, and quality is BadCommunication. The last alarm event is QualityBad. Immediately after restoring the link quality can still be BadCommunication for up to 250 ms, until a fresh acquisition; then it returns to Good with a higher sequence and a QualityRestored alarm event.

Explain it

A GET reads the cache; it does not acquire. Only the acquisition loop mints a new observation. That is why reading more often never makes data fresher, and why the service waits for a new sample after reconnecting rather than reusing the pre-outage one.

Model answers

The event is durable when Append returns after Flush(flushToDisk: true). Delivery is a second appended record, written only after the receiver returns without error. A torn final line is ignored and trimmed on start-up, because that append never completed; a corrupt line in the middle stops start-up, because guessing would hide data loss. The SQL version inserts the outbox row in the same transaction as the batch update, so “batch completed but no event” and “event but batch not completed” are both impossible; two files cannot give that atomicity.

Model answer

A durable command store keeps request ID, request hash, state and expiry across restarts.
